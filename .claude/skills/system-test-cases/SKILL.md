# 시스템 테스트 케이스 생성

테스트 베이시스를 기준으로 SW 시스템 테스트 케이스를 생성한다. 아래 규칙은 모두 필수다.

## 이 프로젝트의 테스트 베이시스

사용자가 따로 지정하지 않으면 다음을 베이시스로 쓴다.

| 출처 | ID 형식 | 읽는 방법 |
|---|---|---|
| GitHub 이슈 | `ISSUE-<번호>` (예: `ISSUE-10`) | `gh issue list --state all --json number,title,body,milestone` |
| README.md 요구사항 | `REQ-<순번>` (README 문장 순서대로 부여) | 파일 읽기 |
| docs/development-plan.md | `PLAN-<절 이름>` | 파일 읽기 |

- 이슈 본문의 "완료 조건", 엔드포인트 표, 오류 응답 항목은 각각 하위 ID로 나눈다 (예: `ISSUE-10.POST-runs`, `ISSUE-3.AC-2`).
- 사용자가 마일스톤이나 이슈 번호로 범위를 지정하면 그 범위만 베이시스로 삼는다.
- 베이시스에 ID가 없어 임시 ID를 부여했으면 그 사실과 부여 규칙을 결과에 적는다.

## 필수 규칙

1. **베이시스 기준**: 모든 테스트 케이스는 베이시스에서 도출하고, 근거 베이시스 ID를 각 케이스에 적는다.
2. **목적 먼저**: 테스트 목적을 먼저 쓰고, 그 아래에 케이스를 쓴다.
3. **커버리지 100%**: 모든 베이시스 항목이 하나 이상의 케이스에 연결되어야 한다. 추적성 표로 검증한 값만 커버리지로 보고한다.
4. **불필요한 케이스 금지**: 커버리지를 채우려는 의미 없는 케이스, 같은 동치 클래스를 중복 검증하는 케이스를 만들지 않는다.
5. **실행 가능성**: 사전조건, 입력값, 절차, 기대 결과가 구체적이고 관찰 가능해야 한다. 수치와 단위를 명시한다. 이 프로젝트에서는 HTTP 요청(메서드, 경로, 본문), 응답 코드, JSON 필드 값, 화면에 표시되는 값처럼 실제로 확인할 수 있는 형태로 쓴다.
6. **기법 적용**: ISO 26262 Part 6 SW Verification 기법을 적용한다. 경계값 분석, 동치 클래스(동등 분할), Pairwise는 반드시 적용한다. 요구사항 기반 테스트, 에러 추정, 오류 주입, 자원 사용 테스트 등은 필요할 때 추가한다.
7. **기법 명시**: 적용한 기법을 각 케이스의 마지막 열에 적는다.
8. **긍정/부정 구분**: 각 케이스에 긍정(Positive) 또는 부정(Negative)을 적는다.
9. **엣지 케이스**: 경계, 극단값, 빈 입력, 최대 크기, 0건/1건, 상태 전이 경계를 포함하고 구분 열에 "엣지"를 병기한다.
10. **제안 표시**: 베이시스에 직접 근거가 없는 케이스는 구분 열에 "제안"을 표시하고, 근거 ID 칸에 가장 가까운 베이시스 ID를, 비고에 제안 사유를 쓴다.
11. **시트 분리**: 기능 테스트와 비기능 테스트를 별도 시트로 나눈다.

## 절차

1. 베이시스를 읽고 항목별로 ID, 기능/비기능 분류, 입력 조건, 기대 동작을 정리한다.
2. 항목별 입력 도메인을 동치 클래스로 나누고 경계값을 뽑는다.
3. 입력 파라미터가 여러 개인 항목(예: 필터 조합, 업로드 필드 조합)은 Pairwise로 조합을 줄이고, 비고에 조합 표 근거를 적는다.
4. 기능 항목은 기능 시트에, 성능·자원 사용·신뢰성·보안·호환성은 비기능 시트에 둔다. 비기능 케이스는 측정 지표와 합격 기준을 수치로 정한다.
5. 목적을 먼저 쓰고 케이스를 쓴다.
6. 추적성 검증: 빠진 베이시스 ID가 있으면 케이스를 추가하고, 어떤 ID에도 연결되지 않고 제안도 아닌 케이스는 삭제한다.
7. 중복 검사: 같은 목적, 같은 동치 클래스, 같은 기대 결과를 갖는 케이스를 합치거나 삭제한다.

## 양식

| 열 | 내용 |
|---|---|
| TC ID | 기능 `TC-F-001`, 비기능 `TC-N-001` |
| 테스트 베이시스 ID | 근거 ID (복수 가능) |
| 테스트 목적 | 검증하려는 것 한 줄 (같은 목적의 케이스는 묶는다) |
| 구분 | 긍정 / 부정, 필요 시 "엣지", "제안" 병기 |
| 사전조건 | 실행 전 상태와 환경 (저장된 차수 수, 서버 기동 여부 등) |
| 입력값 / 절차 | 구체적 값과 단계 |
| 기대 결과 | 관찰 가능한 결과, 수치와 단위 포함 |
| 비고 | 제안 사유, Pairwise 조합 근거 등 |
| 적용 기법 | 경계값 분석 / 동치 클래스 / Pairwise / 기타 |

## 산출물

- 기본 형식은 Excel(.xlsx), 경로는 `docs/test-cases/system-test-cases.xlsx`.
- 시트: `기능 테스트`, `비기능 테스트`, `추적성`(베이시스 ID별 연결 케이스, 제안 여부, 커버리지).
- 생성은 프로젝트 가상환경의 Python과 openpyxl로 한다. openpyxl이 없으면 `.venv/Scripts/pip install openpyxl`로 설치한다. 생성 스크립트는 저장소에 남기지 않는다.
- 마지막에 커버리지 요약을 한 줄로 적는다. 예: `테스트 베이시스 42개 중 42개 연결 (100%), 기능 TC 30개, 비기능 TC 8개, 제안 5개`.

## 하지 말 것

- 베이시스에 없는 기능을 근거 표시 없이 검증하지 않는다.
- 기대 결과를 "정상 동작", "적절히 처리"처럼 모호하게 쓰지 않는다.
- 베이시스가 모호해 기대 결과를 확정할 수 없으면 케이스를 지어내지 않고, 해당 ID와 질문을 목록으로 돌려준다.
- 커버리지를 계산 없이 100%라고 쓰지 않는다.
